# I18n Plugin

Find dead translation keys before they pile up. The i18n plugin statically scans your project for `$dictionary(...)` declarations and reports every key that is never referenced anywhere in the source tree - plus two placeholder checks (see below).

## Quick Start

Register the plugin in `alepha.config.ts` with the `i18n()` helper:

```typescript check filename=alepha.config.ts
import { defineConfig } from "alepha/cli/config";
import { i18n } from "alepha/cli/i18n";

export default defineConfig({
  plugins: [i18n()],
});
```

```bash
alepha i18n check
```

```txt
Checked 412 keys across 187 files (3 dictionary files).

✗ Unused translations (2):
  - profile.legacy.title
  - profile.legacy.subtitle
```

## What It Does

The check extracts every key declared in your `$dictionary(...)` calls, then looks for a quoted-literal reference to each key anywhere else in the scanned files. Keys with no reference are reported and the command exits non-zero - wire it into your verify pipeline so removing a feature can't silently strand its translations. The report also prints an `exempt (dynamic prefixes)` count so exemptions stay visible.

Four more checks run in the same pass:

- **Bad placeholders**: entries using `{0}`-style placeholders that never interpolate; Alepha interpolates `$1`, `$2` and `{name}`, and a name is never a number.
- **Missing arguments**: `tr()` calls passing fewer arguments than the entry's `$N` placeholders expect.
- **Missing names**: `tr()` calls that leave a `{name}` of the entry unfilled, across every variant of a variant entry. A name missing from `args: { ... }` is reported, and every name when the call passes positional `args: [...]` or none. `{count}` is filled by the `count` option, not by `args`, so a call using it with no `count` is reported too. An escaped `{{name}}` is text.

- **Plural categories**: each plural entry is checked against the rules of its catalog's language (see below).

Like the argument count, the name check reports only what it can prove: a call whose options or `args` are a variable or a spread is left alone.

## Plural Categories

A plural entry that compiles can still be wrong in another language: a Polish entry that copies the English `one` and `other` shows the wrong form for 2, 3, 4 and 5. The check reads the variant names of each entry and compares them with `Intl.PluralRules` for the language of its catalog.

- **Required** (an error when missing): `other`, plus every category the language selects for the whole numbers 0 to 200. That is `one` for English and French, `one`, `few` and `many` for Polish, and `zero`, `one`, `two`, `few` and `many` for Arabic.
- **Allowed**: the language's own categories (`resolvedOptions().pluralCategories`). French `many`, which only 1,000,000 and its multiples select, is allowed and not required.
- **Anything else is a warning**: printed, but it does not fail the check.
- **A key that is a variant object in one language and a plain string in another is an error.** A language with no plural distinction writes `{ other: "..." }` alone, so the call site passes a `count` in every language.

The language of a catalog is the property name of its `$dictionary` or its `lang` option, for a lazily imported key file (`lazy: () => import("./pl.ts")`) and for an inline object alike. A record spread into a dictionary (`...uiFr`) has no provable language and is not checked.

An entry whose variant names are all plural categories (`zero`, `one`, `two`, `few`, `many`, `other`) is read as plural, unless a call passes it `select:`. An entry with any other variant name is a select, and the check leaves it alone.

If no translation keys are found at all, the command exits with code `2` and a warning - that usually means the dictionary location changed and the scan is looking in the wrong place.

## Configuration

`i18n()` accepts the following options:

| Option            | Type       | Default   | Description                                                                                                                     |
| ----------------- | ---------- | --------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `scan`            | `string[]` | `["src"]` | Directories (relative to the project root) to scan for dictionaries and key usage                                               |
| `dynamicPrefixes` | `string[]` | `[]`      | Key prefixes constructed at runtime - exempted from the check                                                                   |
| `exclude`         | `string[]` | `[]`      | Extra path substrings to exclude, on top of the defaults (`node_modules`, `dist`, `__tests__`, `.spec.*`, `.test.*`, `.alepha`) |

```typescript check filename=alepha.config.ts
import { defineConfig } from "alepha/cli/config";
import { i18n } from "alepha/cli/i18n";

export default defineConfig({
  plugins: [
    i18n({
      scan: ["src", ".vendor/@alepha/ui"],
      dynamicPrefixes: ["folio.type.", "feedback.filter."],
    }),
  ],
});
```

## Dynamic Keys

A key built with a template literal has no quoted-literal reference:

```typescript
tr(`folio.type.${kind}`);
```

The static scan can't see it, so every `folio.type.*` key would be reported as unused. Add the prefix to `dynamicPrefixes` to exempt them.

> **Audit your prefixes**
>
> Keep the `dynamicPrefixes` list short and re-check it when a feature is removed - a stale prefix is a place where dead keys can hide.

## In the Verify Pipeline

Add a `check:i18n` script to your app and let CI run it:

```json filename=package.json
{
  "scripts": {
    "check:i18n": "alepha i18n check"
  }
}
```

The exit codes make it CI-friendly: `0` clean (plural warnings included), `1` unused keys, bad placeholders, missing arguments, missing names or plural errors found, `2` no keys found at all.
